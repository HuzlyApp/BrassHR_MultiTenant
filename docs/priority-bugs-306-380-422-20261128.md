# BUG-306, BUG-380 and BUG-422 — 2026-11-28

Prepared by HENERALPEPITO <clelipan@up.edu.ph>.

## Implementation

- BUG-306: isolated anonymous applicant credentials live only in memory. The first application receives a tenant/job/session-bound two-hour grant, which cannot be renewed after expiry or submission. Browser reload or later entry with an earlier applicant cookie requires candidate sign-in; Different person explicitly expires the old grant and clears applicant context. Signed-in candidates/workers use their actual portal client, preserving staff isolation. Continuation links route through sign-in, public job links cannot claim applications, and restart URLs contain a single job_token. API and restrictive Data API/Storage policies enforce the same grant boundary.
- BUG-380: staff OTP, OAuth and new-workspace login bindings establish durable activity against the verified Auth session_id. Ordinary reads and background checks do not renew it. Trusted foreground input sends a throttled activity POST; expired sessions cannot be revived or rebound. The database enforces 30-minute idle and 12-hour absolute limits, marks expiry durably, and the server revokes that session's refresh tokens. A missing/edited activity cookie does not reset staff expiry. Existing staff sessions without a new activity record require sign-in after rollout.
- BUG-422: candidate-added profession document fields carry worker_id. Global settings/public workflow configuration exclude these fields, candidate views include only shared and own fields, candidate payloads cannot alter shared requirements, and upload lookups reject another candidate's field. Labels, expiry metadata, files and review records remain on the target candidate.
